# متابعة أرصدة الموردين — Supplier Balance Watch

شاشة داخل الأبلكيشن (`supplier_balances.html`) بتخلّي المستخدم يلصق كشف أرصدة موردين الفرع كنص،
تتقارن مع آخر كشف محفوظ لنفس الفرع، وتطلّع 3 أقسام: أرصدة اتغيّرت / موردين ظهروا لأول مرة /
موردين اختفوا من الكشف. مع بحث داخل النتائج، تصدير CSV (بـ BOM للعربي)، استثناءات عامة،
وحد لتجاهل الفروق الصغيرة.

## ⚠️ ملاحظة أمان صريحة (اقرأها)

- **كل التحقق من الصلاحيات في الشاشة دي client-side، وبنفس مستوى باقي الأبلكيشن — لا أقوى ولا أعلى.**
- **الـ RLS على جداول الشاشة مفتوحة (`anon`/`authenticated`) زي باقي جداول الأبلكيشن، والمفتاح anon عام؛
  يعني مفيش فرض صلاحيات حقيقي على مستوى السيرفر.** إخفاء الصفحة وتعطيل الأزرار هدفهم منع الاستخدام الطبيعي الغلط،
  مش الحماية ضد حد بيتعامل مع الـ API مباشرة.
- `taken_by` / `run_by` (مين عمل العملية وإمتى) بتتسجّل من بيانات المستخدم المحلية **للتتبّع والمراجعة فقط،
  وهي بيانات غير موثّقة** (مش مصدر ثقة).

## الصلاحيات (النموذج الفعلي في الأبلكيشن)

نظام الصلاحيات في الأبلكيشن **على مستوى الصفحة لكل دور** عبر جدول `page_permissions(role, page, can_view, can_edit)`
والـ RPC `get_role_pages`. مفيش نظام صلاحيات على مستوى الأفعال (action-level)، فاتّبعنا نفس النمط:

| الصلاحية المطلوبة في المواصفات | الما بيقابلها هنا |
|---|---|
| `suppliers.balance_watch.view` | `can_view` = دخول الشاشة وعرض النتائج |
| `suppliers.balance_watch.import` | `can_edit` |
| `suppliers.balance_watch.undo` | `can_edit` |
| `suppliers.balance_watch.exclusions` | `can_edit` |
| `suppliers.balance_watch.settings` | `can_edit` |

يعني: **`can_view`** = يشوف. **`can_edit`** = كل عمليات الكتابة (لصق/مقارنة/حفظ + تراجع + استثناءات + إعدادات).
التحقق كله بيعدّي على مكان واحد في الكود — الدالة `act()` في `supplier_balances.html` — وكل زرار كتابة بيستخدمها،
وكمان بيتعطّل بصريًا مع رسالة واضحة من غير صلاحية `can_edit`. من غير `can_view` بيحصل route guard (شاشة «غير مصرّح»).

### التوزيع على الأدوار
- **افتراضيًا: الأدمن بس** (view + edit) — متزرّع في الميجريشن.
- **توزيع view لأي دور**: من شاشة **الصلاحيات** (مصفوفة الأدوار) — علّم العمود بتاع الصفحة للدور.
  مصفوفة الأدوار بتدير **`can_view` بس** (زي كل الشاشات؛ `save_page_permissions_bulk` بيحدّث `can_view` فقط
  وبيسيب `can_edit` زي ما هو). الدور اللي بياخد view من المصفوفة بياخد **عرض فقط** على الشاشة دي.
- **منح `can_edit` لدور تاني** (لو محتاج): لازم تتعمل مباشرة في القاعدة (المصفوفة بتدير view بس):
  ```sql
  update public.page_permissions set can_edit = true
  where role = '<الدور>' and page = 'supplier_balances.html';
  ```

## سكوب الفرع
`admin` و`accountant` بيشوفوا تبويبات كل الفروع؛ أي دور تاني بيشوف تبويب فرعه بس (`userBranch`) — نفس منطق
`shift_history.html`. أسماء الفروع بتيجي من جدول `branches` (مش ثابتة في الكود).

## التخزين (append-only)
- `supplier_balance_snapshots` و`supplier_balance_runs` = **إضافة فقط، لا UPDATE ولا DELETE إطلاقًا**
  (مفروض على مستوى الـ RLS: بوليسي SELECT + INSERT بس). أي لصق غلط يفضل قابل للاسترجاع.
- **المرجع الحالي لأي فرع = أحدث صف** في `snapshots` بـ `taken_at`.
- **«تراجع» = إضافة صف جديد** (`kind='undo'`) بينسخ السناب شوت الأقدم ويشاور عليه بـ `restored_from` —
  مش تعديل ولا حذف.
- `supplier_balance_exclusions`: قائمة استثناءات عامة (إضافة/حذف).
- `supplier_balance_settings`: صف واحد لحد تجاهل الفروق (مشترك بين الكل).
- السكيمة الكاملة في [`supplier_balances.sql`](../supplier_balances.sql) (متطبّقة كـ migration `supplier_balance_watch`).

## تشغيل تست الـ parser
```bash
node tests/supplier_balances_parser.test.js
```
بيغطّي: سطر عناوين بترتيب أعمدة مختلف، سالب بشكل `1.000-`، سالب بالأقواس، أرقام عربية، أعمدة فاضية،
كود نصّي، سطور فاضية، وسطور بتتخطّى (كود غير صالح + رصيد غير رقمي)، وكمان `compare` (تغيّر/جديد/اختفى + الحد + الاستثناءات).

## ملاحظات مقصودة (تختلف عن النموذج)
- **الحفظ التلقائي دايمًا شغّال** (مفيش توجل): بحكم إن التخزين append-only، كل لصق بيتحفظ كمرجع جديد
  والقديم يفضل موجود للتراجع. ده أأمن من فكرة «قارن من غير حفظ».
- **تعديل أسماء الفروع** اتشال: الأسماء بتيجي من جدول `branches`.
